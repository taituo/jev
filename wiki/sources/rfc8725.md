# RFC 8725 — JWT Best Current Practices

RFC 8725 gives current security guidance for JWT implementers and
deployers; the whole document is security considerations
(RFC 8725 §4).

## Algorithm and crypto hygiene

- Libraries MUST let callers specify supported algorithms and MUST NOT
  use others; each key MUST be used with exactly one algorithm
  (RFC 8725 §3.1).
- Applications MUST only allow cryptographically current algorithms and
  stay agile as algorithms age (RFC 8725 §3.2).
- JWTs using `none` SHOULD NOT be generated or consumed unless
  explicitly requested; `none` is acceptable only when otherwise
  protected such as by TLS (RFC 8725 §3.2).
- RSA PKCS1 v1.5 encryption SHOULD be avoided in favor of RSAES-OAEP
  (RFC 8725 §3.2).
- All cryptographic operations MUST validate; reject the whole JWT on
  any failure (RFC 8725 §3.3).
- ECDH inputs MUST be validated per the cited NIST routine or RFC 8037
  considerations (RFC 8725 §3.4).
- Human-memorizable passwords MUST NOT be used directly as HS256 keys
  (RFC 8725 §3.5).
- Compression before encryption SHOULD NOT be done (RFC 8725 §3.6).
- UTF-8 MUST be used for headers and claims sets (RFC 8725 §3.7).

## Identity and confusion resistance

- When `iss` is present, the keys MUST belong to the issuer or the JWT
  MUST be rejected; `sub` MUST correspond to a valid subject or pair
  (RFC 8725 §3.8).
- Multi-audience issuers MUST include `aud`; recipients MUST validate
  it and MUST reject missing or foreign values (RFC 8725 §3.9).
- Do not blindly trust `kid`, `jku`, or `x5u`; validate and sanitize to
  avoid injection and SSRF (RFC 8725 §3.10).
- Explicit typing with `typ` is RECOMMENDED for new JWT uses; for nested
  JWTs the inner `typ` MUST be present (RFC 8725 §3.11).
- Validation rules for different JWT kinds from one issuer MUST be
  mutually exclusive (RFC 8725 §3.12).
