# RFC 7519 — JSON Web Token (JWT)

RFC 7519 defines JWT as a compact claims representation for space-constrained
environments such as HTTP Authorization headers and URI query parameters
(RFC 7519 §1). A JWT encodes claims as a JSON object used as a JWS payload
or JWE plaintext (RFC 7519 §1).

## Claims

- No claim is mandatory in all cases; applications define which claims are
  required or optional (RFC 7519 §4.1).
- `iss` identifies the principal that issued the JWT; use is OPTIONAL
  (RFC 7519 §4.1.1).
- `sub` identifies the principal that is the subject; use is OPTIONAL
  (RFC 7519 §4.1.2).
- `aud` identifies the intended recipients; if present and the processor
  does not identify with an `aud` value, the JWT MUST be rejected; use is
  OPTIONAL (RFC 7519 §4.1.3).
- `exp` identifies the expiration time; after it the JWT MUST NOT be
  accepted; small clock-skew leeway MAY be allowed; use is OPTIONAL
  (RFC 7519 §4.1.4).
- `nbf` identifies the time before which the JWT MUST NOT be accepted;
  use is OPTIONAL (RFC 7519 §4.1.5).
- `iat` identifies when the JWT was issued; use is OPTIONAL
  (RFC 7519 §4.1.6).
- `jti` provides a unique identifier to prevent replay; use is OPTIONAL
  (RFC 7519 §4.1.7).
- Claims not understood MUST be ignored absent application requirements
  (RFC 7519 §4).

## JOSE header

- `typ` declares the media type; RECOMMENDED value is `JWT`; the parameter
  is ignored by JWT implementations and use is OPTIONAL (RFC 7519 §5.1).
- `cty` conveys structural information; in nested signing/encryption it
  MUST be present with value `JWT`; otherwise its use is NOT RECOMMENDED
  (RFC 7519 §5.2).
- Claims MAY be replicated as JWE header parameters; receivers SHOULD
  verify replicated values are identical (RFC 7519 §5.3).

## Unsecured, creation, validation

- Unsecured JWTs MAY be created without signature or encryption using
  `alg` `none` with an empty signature when content is secured by other
  means (RFC 7519 §6).
- Creation follows JWS or JWE steps with an optional nested `cty` `JWT`
  pass (RFC 7519 §7.1).
- Validation MUST reject the JWT if any listed step fails
  (RFC 7519 §7.2).
- The final algorithm-acceptance check is application decided; even a
  valid JWT SHOULD be rejected if its algorithms are unacceptable
  (RFC 7519 §7.2).

## Implementation requirements

- Of JWA signature/MAC algorithms, only `HS256` and `none` MUST be
  implemented; `RS256` and `ES256` are RECOMMENDED (RFC 7519 §8).
- Encrypted-JWT support is OPTIONAL; if provided, `RSA1_5`, `A128KW`,
  `A256KW`, `A128CBC-HS256`, and `A256CBC-HS512` MUST be implemented
  (RFC 7519 §8).
- Nested JWT support is OPTIONAL (RFC 7519 §8).
